## 第一部分: 后端架构设计

### 1. 架构概述

#### 1.1 架构选型

**采用架构**: **分层架构 (Layered Architecture)**

**选型理由**:
- ✅ 适合 MVP 阶段的快速开发
- ✅ 职责清晰,易于维护和测试
- ✅ 符合团队现有技能栈
- ✅ 支持未来扩展到微服务架构

#### 1.2 整体架构

```
┌─────────────────────────────────────────────────────────┐
│                    Client (Frontend)                      │
│              (Vue3 + Uni-app / HBuilderX)               │
└─────────────────────────┬───────────────────────────────┘

│  │  - 响应封装 (ApiResponse)                          │  │

│  └───────────────────┬───────────────────────────────┘  │
```

### 2. 分层架构详解

#### 2.1 API Layer (`app/api/`)

**职责**:
- 定义 RESTful API 接口
- 请求参数验证
- 响应数据封装
- 认证授权检查
- 调用 Services 层处理业务

**目录结构**:
```
app/api/
├── __init__.py
├── auth.py          # 认证接口
├── goals.py         # 目标接口
├── plans.py         # 规划接口
└── tasks.py         # 任务接口
```

**设计原则**:
- API 层不包含业务逻辑,只负责参数转换和调用
- 统一响应格式封装
- 统一异常处理

---

#### 2.2 Services Layer (`app/services/`)

**职责**:
- 封装业务逻辑
- 数据组装和转换
- 事务管理
- 调用 Core 层和 Models
- 跨模块的业务编排

**目录结构**:
```
app/services/
├── __init__.py
├── auth_service.py     # 认证业务逻辑
├── goal_service.py     # 目标业务逻辑
├── plan_service.py     # 规划业务逻辑
└── task_service.py     # 任务业务逻辑
```

**设计原则**:
- 业务逻辑集中管理
- 可复用的业务逻辑封装
- 事务边界清晰

---

#### 2.3 Core Layer (`app/core/`)

**职责**:
- 核心算法实现(如 AI 调用逻辑)
- 配置管理
- 安全工具(密码加密、JWT)
- 数据库连接管理
- 抽象基类定义

**目录结构**:
```
app/core/
├── __init__.py
├── config.py           # 配置管理
├── database.py         # 数据库连接
├── security.py         # 安全工具(JWT、密码加密)
├── ai_engine.py        # AI 引擎(调用 DeepSeek)
├── dependencies.py     # FastAPI 依赖
├── exceptions.py       # 自定义异常
└── response.py         # 统一响应格式
```

**设计原则**:
- 核心组件独立封装
- 配置统一管理
- 安全组件集中实现

---

#### 2.4 Utils Layer (`app/utils/`)

**职责**:
- 通用工具类
- 日志配置
- 数据验证器
- 性能监控工具

**目录结构**:
```
app/utils/
├── __init__.py
├── logger.py           # 日志配置
├── validators.py       # 数据验证器
└── timer.py            # 性能计时器
```

**设计原则**:
- 工具类无状态
- 功能单一职责
- 可测试性强

---

#### 2.5 Models Layer (`app/models/`)

**职责**:
- 定义 SQLAlchemy ORM 模型
- 数据库表结构映射
- 模型之间的关系定义

**目录结构**:
```
app/models/
├── __init__.py
├── user.py             # 用户模型
├── goal.py             # 目标模型
├── plan.py             # 规划模型
└── task.py             # 任务模型
```

**设计原则**:
- 模型只负责数据结构定义
- 业务逻辑放在 Service 层
- 关系清晰明确

### 3. 设计模式应用

#### 3.1 依赖注入 (Dependency Injection)

**使用场景**: FastAPI 依赖注入系统

**设计要点**:
- 数据库会话注入
- 用户认证信息注入
- 可复用的依赖项

**优势**:
- 降低模块间耦合
- 便于单元测试
- 提高代码可维护性

---

#### 3.2 DTO 模式 (Data Transfer Object)

**使用场景**: 请求和响应数据模型

**设计要点**:
- 使用 Pydantic 定义
- 自动参数验证
- 类型安全

**优势**:
- 数据验证集中管理
- 接口文档自动生成
- 减少重复代码

---

#### 3.3 统一响应格式

**响应结构设计**:
- `code`: 响应码(0 表示成功)
- `message`: 响应消息
- `data`: 响应数据

**优势**:
- 前端处理统一
- 错误处理规范化
- 便于日志监控

### 4. 认证方式设计

#### 4.1 认证方式: 用户名 + 密码

**设计理由**:
1. **简单直接**: 适合 MVP 阶段,开发成本低
2. **文档一致性**: 与 API 文档设计保持一致
3. **用户友好**: 用户名比手机号更灵活,无需验证码
4. **隐私友好**: 不需要收集手机号等敏感信息

#### 4.2 认证流程

```
┌─────────┐                    ┌─────────┐
│ Client  │                    │ Server  │
└────┬────┘                    └────┬────┘
     │                              │
     │ 1. POST /api/auth/register  │
     │    {username, password,     │
     │     email}                  │
     ├─────────────────────────────>│
     │                              │
     │                              │ 2. 检查用户名是否存在
     │                              │ 3. 加密密码
     │                              │ 4. 创建用户
     │                              │ 5. 生成 JWT Token
     │                              │
     │ 6. {token, user_id}         │
     │<─────────────────────────────┤
     │                              │
     │ 7. 保存 Token               │
     │                              │
     │ 8. GET /api/goals           │
     │    Header: Authorization:   │
     │      Bearer {token}         │
     ├─────────────────────────────>│
     │                              │
     │                              │ 9. 验证 JWT Token
     │                              │ 10. 提取 user_id
     │                              │ 11. 查询用户数据
     │                              │
     │ 12. {code: 0, data: goals} │
     │<─────────────────────────────┤
```

#### 4.3 JWT Token 设计

**Token 结构**:
- `sub`: 用户 ID
- `exp`: 过期时间(7 天后)
- `iat`: 签发时间

**安全设计**:
- 使用 HS256 算法
- 强密钥(至少 32 字符)
- 可配置过期时间

### 5. 错误处理设计

#### 5.1 错误码定义

**错误码分类**:
- `1001-1099`: 认证相关错误
- `2001-2099`: 目标相关错误
- `3001-3099`: 规划相关错误
- `4001-4099`: 任务相关错误
- `10001-10099`: AI 服务错误

**常见错误码**:
- `1001`: 用户名已存在
- `1003`: 用户不存在
- `1004`: 密码错误
- `2001`: 目标不存在

#### 5.2 异常处理策略

**处理原则**:
- 业务异常: 自定义异常类,返回明确错误码
- 系统异常: 统一捕获,返回通用错误信息
- 日志记录: 所有异常必须记录日志

### 14. AI Prompt 设计

#### 14.1 System Prompt

**设计目标**:
- 明确 AI 的角色定位
- 定义输出格式要求
- 规划生成的质量标准

**核心要素**:
- 角色定位: 专业的目标规划助手
- 任务说明: 分解目标为可执行任务
- 输出要求: 标准 JSON 格式
- 质量控制: 阶段数量、任务数量、时间估算

---

#### 14.2 User Prompt 生成策略

**输入参数**:
- goal_title: 目标标题
- goal_description: 目标描述
- deadline: 期望完成时间
- available_hours: 每天可用时间

**生成逻辑**:
1. 组装目标信息
2. 添加生成要求
3. 指定输出格式
4. 返回完整 Prompt

**输出格式要求**:
- JSON 格式
- stages 数组
- 每个阶段包含: name, order, description, tasks
- 每个任务包含: title, description, estimated_hours, order

---

### 15. 任务自动创建算法

#### 15.1 日期分配逻辑

**核心步骤**:
1. 计算可用天数(从今天到截止日期)
2. 遍历规划中的所有任务
3. 按顺序分配日期(可选择跳过周末)
4. 设置任务截止时间(默认上午 9 点)

**考虑因素**:
- 任务顺序
- 预估工时
- 可用天数
- 是否跳过周末

---

### 16. 错误处理与降级

#### 16.1 AI 调用失败处理

**错误类型**:
- API_KEY_INVALID: API 密钥无效
- API_QUOTA_EXCEEDED: 配额超限
- AI_SERVICE_UNAVAILABLE: 服务不可用
- AI_GENERATION_FAILED: 生成失败
- INVALID_RESPONSE_FORMAT: 响应格式错误

**降级方案**:
- 提供模板规划
- 使用预设的阶段划分
- 基于目标标题生成通用任务

#### 17.1 成本因素

**影响因素**:
- API 调用次数
- 输入 Token 数量
- 输出 Token 数量
- 服务商定价

**成本优化策略**:
- 减少 Prompt 长度

## 第四部分: 认证安全设计

### 18. 认证方案概述

#### 18.1 采用方案: JWT (JSON Web Token) Bearer Token 认证

**选型理由**:
- ✅ 无状态,适合前后端分离架构
- ✅ 跨域支持友好
- ✅ 移动端支持良好
- ✅ 可扩展性好

---

### 19. 安全配置要求

#### 19.1 JWT 配置

**安全要求**:
- JWT_SECRET_KEY: 必须保密,至少 32 字符
- JWT_ALGORITHM: 使用 HS256
- JWT_ACCESS_TOKEN_EXPIRE_MINUTES: 可配置,默认 7 天

**密钥管理**:
- 生产环境使用强密钥
- 定期轮换密钥
- 不要硬编码在代码中
- 使用环境变量管理

---

#### 19.2 密码安全

**加密方案**: bcrypt

**安全特性**:
- 自动盐值管理
- 自适应加密算法
- 防止彩虹表攻击
